## 小程序代码必然下发到手机：客户端保密是伪命题
- 2026-09-21

**结论**：小程序以 wxapkg **整包下发**到手机本地（首次打开下载、之后离线可用），且 JS 不真正编译（WXML/WXSS 转成 JS 渲染函数）——解包可读是**所有小程序的共性**，不是某家的漏洞。但解包只能得到「接口说明书」（API 地址、请求格式、前端校验、偶尔忘删的测试接口），得不到「钥匙」（后端业务逻辑、密钥、wx.login 背后的微信身份签发）。判断客户端体系安全的标准：**把秘密放在客户端的迟早泄密，把客户端当透明设计的无秘可泄。**

**细节**：

双线程模型：逻辑层 JS 独立线程（JSCore）+ 渲染层（WebView/Skyline），桥接通信——隔离设计带来安全管控，也决定了只能解释执行，堵死了原生 App 的编译加壳防护路线。

解包边界表：

| 能看到 | 拿不到 |
|---|---|
| 页面结构、交互逻辑 | 服务端业务逻辑（判定、令牌签发、风控） |
| API 地址与请求/响应格式 | 数据库、账号数据 |
| 前端校验（如二维码格式） | 真正的密钥（守规矩的开发者只放服务端） |

开发者防御层次（弱→强）：压缩混淆（只是门槛）→ 敏感逻辑全部后置（正确姿势）→ 热更新动态下发 → 平台沙箱（小程序能拿的手机权限远小于原生 App，双刃剑：防护浅、可造成的危害也小）。

法律边界：微信平台规则禁止逆向；还原他人小程序代码涉嫌著作权/不正当竞争（有判例）；用解包知识向系统发伪造请求 = 未授权访问。

**坑**：小厂小程序被「协议破解」惨案的根因是签名算法/密钥写死在 JS 里 **且** 服务端不校验请求合理性——客户端泄密+服务端裸奔叠加才出事，属开发者水平问题而非平台宿命。

## 小程序版与App版功能差异的判断标准
- 2026-09-21

**结论**：小程序版通常是 App 版的功能子集，根源是**运行环境与权限边界**（小程序寄生微信进程、只能调 wx.* 接口子集），不是代码质量。判断式：功能只依赖「登录态+界面+发请求」→ 两版可完全对齐（查询/表单/扫码类，如打卡类应用）；需要后台常驻/推送/深度硬件 → 小程序必然阉割。两版通常共用同一后端与账号，数据互通。

**细节**：

关键差异点：
- 后台：App 可常驻/自启；小程序切后台很快被挂起；
- 推送：App 自由推送；小程序只有订阅消息，一次授权一条；
- 体积：小程序主包限几 MB、整包几十 MB 级；App 可上百 MB；渲染为 WebView/自绘引擎，长列表/动画/游戏明显吃力；
- 硬件：文件系统仅沙箱目录；蓝牙有接口但受限；NFC 基本只能读 NDEF；后台定位无缘；
- 小程序反向独有优势：微信一键登录、支付内嵌、社交分享深度集成、**热更新静默全量生效**（App 版本碎片化严重）。

**坑**：产品做双版的动机常被误解为「技术冗余」——实际是「App 保深度、小程序抢流量」的分工。

## 沙箱运行小程序的三条途径与边界
- 2026-09-21

**结论**：三条公开途径：①**官方微信开发者工具**（本质就是官方沙箱模拟器，配 miniprogram-automator 可脚本化，但只对自有源码的项目友好）；②**安卓模拟器/云手机跑完整微信**（兼容最好，但模拟器指纹——构建特征、无传感器、x86 痕迹——可被风控识别，云手机比 x86 模拟器更难识别）；③**第三方小程序容器**（商业 FinClip、开源 wept/hera 等，API 覆盖永远滞后，运行别人的小程序有著作权问题）。沙箱模拟的是「**运行时**」（渲染/JS/常规 API），模拟不了「**信任链**」（wx.login 需与微信服务器真实认证握手、第三方运行时无法合法签发；小程序服务端的登录态/动态令牌验证/风控与运行环境无关）。**沙箱换掉的恰恰是唯一不被信任的那一层。**

**坑**：①以为沙箱能解决「在场证明」是类别错误——动态令牌要求物理在机器前扫到，那是物理问题不是客户端问题；②模拟器环境（传感器缺失、自动化操作痕迹）在风控眼里比真人真机**更醒目**，自动化收益常为负。
